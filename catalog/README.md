# Ingredient catalogue builder

Build a separate SQLite ingredient catalogue from pinned public downloads:

```sh
python3 scripts/build-ingredients.py catalog/manifest.json --output .runtime/ingredients
python3 scripts/audit-ingredients.py \
  --baseline catalog/legacy-identities.json \
  --output .runtime/ingredients --decisions catalog/legacy-mappings.json
```

Requires Python 3.10+. On Python versions without native Zstandard support, install the `zstd` executable to read compressed installer sources; the Docker image includes it. Add `--offline` to rebuild from the verified download cache; `--cache PATH` chooses its location. Downloads and generated ingredient data belong in ignored `.runtime/`, not in Git.

The builder produces an **ingredient-only database**, not an application backup. Its four ingredient tables use Brewey's existing `id`/JSON `data` layout. The standalone builder does not change an application database, cloud data or recipes. With the default manifest it also writes a separate `styles.json` containing downloaded BJCP 2021 descriptions. Setup imports those descriptions into empty text fields without changing style IDs, brewing statistics or existing notes. First-run setup and Settings → Ingredients use this builder through an administrator-only background job. Hosted exports use a separately compiled identity index from the reviewed audit.

## Outputs

- `styles.json`: downloaded style prose, separate from the ingredient tables; unavailable downloads leave an empty array and a partial report. `catalog/styles.json` pins the source and matches all 123 supported styles by name, including substyles that share source numbers.
- `ingredients.sqlite` and `catalog.json`: deduplicated ingredients in Brewey's schema.
- `beerjson.json`: BeerJSON 1.0 ingredient collections; `beerjson-ids.json` associates each array position with its permanent Brewey ID.
- `provenance.json`: source records, field winners, corrections, per-ingredient content hashes and retained source properties.
- `retired-id-map.json`: redirects from explicitly merged duplicate IDs to their surviving IDs. Consumers must still check that a target is available in a partial build.
- `conflicts.json`: differing values resolved by source priority.
- `build-report.json`: source availability, rejected records, repairs, counts and fingerprints needing identity review.
- `AUDIT.md`, `audit.json`, `missing.json`, `excluded-legacy.json`, `cloud-id-map.json`: generated by the audit command. Proposed substitutions and intentional exclusions are separate; fuzzy suggestions never count as matches. Despite its historical filename, `cloud-id-map.json` maps the supplied baseline IDs, which are not verified production UUIDs.

## Sources and identity

`manifest.json` selects public sources and pins their SHA-256 checksums. Lower numerical priority wins; manifest order breaks ties. Current manufacturer files take precedence, followed by newer named-brand packs, other brand packs, general updates (newest first), installer base definitions and retailer supplements. A file being hosted by BeerSmith does not establish who authored it. `source-selection.json` records excluded translations and redundant packs.

Each source has an ordered `locations` list. These are alternate downloads of that source, not additional packs to merge. An unavailable, changed, malformed or unusable download tries the next location. Optional failures leave a partial catalogue and a report; required failures stop the build. An entirely unsuccessful build fails without replacing existing outputs. Re-running retries missing files, uses checksum-verified cached files, and rebuilds the outputs without accumulating duplicate records.

The four base definitions share one pinned installer download. The builder reads individual archive members in memory; it never installs or executes the package. Each member has its own checksum. Where an older selected pack also overlaps a newer pack, it can supply records when the preferred pack is unavailable. Gladfield additionally has a manufacturer-download/CDN fallback pair.

`identities.json` is the permanent identity registry. It maps normalised source fingerprints to stable keys; UUIDv5 hashes those keys under a fixed namespace. Descriptions, brewing numbers, source order and source availability do not enter the ID. Brand, origin, product code and physical form are preserved where they distinguish products. Reviewed spelling aliases, renamed varieties and distributor duplicates share a key. Codes reused for different products are not blindly merged. A `+` suffix remains distinct, including modified yeast variants.

**Keep established keys and the namespace unchanged.** To rename or merge an ingredient later, point the new fingerprints at an existing key. Do not regenerate keys from whichever source happens to be available. Unrecognised fingerprints receive deterministic provisional IDs and appear in the build report for review. This is deterministic conversion and registry lookup; no model is called during installation.

## Supplying or updating a manifest

The format is JSON:

```json
{
  "version": 1,
  "registry": "identities.json",
  "sources": [{
    "id": "example-manufacturer",
    "format": "bsmx",
    "priority": 10,
    "required": false,
    "locations": [{
      "url": "https://example.org/ingredients.bsmx",
      "sha256": "<64 lowercase hex characters>"
    }]
  }]
}
```

Supported input adapters are `bsmx`, `beerxml` and `reviewed-json`. A location can use `path` instead of `url`, relative to the manifest. Debian archive locations additionally specify `member` and `member_sha256`. Shared conversion handles units and supported categories. Unsupported types or invalid required values are reported, not silently assigned a default.

`supplement.json` supplies reviewed manufacturer facts absent from available import files, with original concise descriptions. It is a pinned local manifest source and needs no download or AI during installation. Each record carries its ingredient table, app-schema `data` in Celsius/percent units, supported `extra` properties, credential-free HTTPS evidence URLs, review date and qualifications in its review reason. Yeast attenuation is the midpoint of its accompanying range. Unknown optional values remain null. A malformed supplement fails as a unit. Its evidence is retained in generated provenance.

The supplement is required because it ships with the builder; external sources remain optional. With an empty cache and no network, the builder can produce only the bundled supplement and explicitly reports a partial catalogue. First-run setup reports this partial result and lets the administrator continue or retry. Settings → Ingredients offers the same retry controls.

To update a source, inspect its new contents, update the checksum, rebuild into a review directory, inspect conflicts/unregistered fingerprints and rerun the audit. Add aliases or reviewed overrides to the registry when warranted. Blank values never overwrite useful values from another source. Numeric zero and `false` remain meaningful values. Reversed attenuation bounds are sorted with recorded evidence; ranges outside the supported schema are omitted with their original values retained in provenance.

Sugar, honey, juice and extract records are corrected when a source incorrectly requires an enzymatic mash. Barley-style analytical defaults on non-grain fermentables remain in provenance but are excluded from the BeerJSON projection. Generated timestamps use a fixed epoch for repeatability; they are not manufacturer publication dates. Source checksums and content hashes identify the actual versions.

BeerJSON retains producer and supported additional properties alongside the simpler app projection. The app still combines fermentable type and grain group, represents attenuation as a midpoint, and has fewer culture categories. Generic grain/base/specialty classification uses conservative name rules plus reviewed overrides; importing a manufacturer file is not independent verification of every supplied brewing value. Inventory, prices and recipe quantities are excluded.

`legacy-mappings.json` contains reviewed migration decisions for the existing reference catalogue. It does not write to the cloud. Some decisions deliberately substitute a commodity supplier or dry yeast variant; they are not assertions of exact formulation equivalence. Hosted exports retain source brewing properties and check calculations; matching an identity does not replace those properties with the new catalogue's values.

`migration-rules.json` records scoped decisions for cloud exports. In particular, the US-grown production Saaz entry maps to Saaz U.S.; that rule must not be applied to Czech Saaz or to a name without an origin. Reviewed legacy exclusions document what may be omitted from the new catalogue, not permission to delete production data or discard an ingredient used by an exported recipe.

After an audited complete build, run `python3 scripts/compile-ingredient-migration.py --build .runtime/ingredients` to regenerate `frontend/src/lib/server/ingredient-migration-index.json` (or add `--check` to verify it). The compiler reruns the reviewed audit and emits identity selectors and stable IDs only, without descriptions or brewing specifications. The hosted exporter matches these selectors rather than assuming baseline UUIDs are production UUIDs. Matching ignores casing and repeated whitespace; it does not use fuzzy names or broaden an origin/form match. Ambiguous selectors and unknown ingredients retain private export identities. Exported recipe ingredients retain their source brewing values, and a later catalogue download preserves used rows.

## Quality review

```sh
python3 scripts/review-ingredient-quality.py --output .runtime/ingredients \
  --decisions catalog/quality-decisions.json
```

This creates `quality-report.json`, screening all generated records for missing/long descriptions, shared descriptions, repeated yeast codes, suspicious zero extract, classification conflicts and large numeric disagreements. These are review candidates, not automatic corrections or proof of duplication. Numeric overrides and reviewed aliases belong in `identities.json`, with reasons and evidence. Register retired identity keys in `redirects` when merging established entries.

`quality-decisions.json` records evidence for retained values and deliberately distinct products. A decision binds to the exact ingredient IDs, issue and values; changed findings require a new review. The report keeps all findings visible and separates unresolved actionable counts. Paired attenuation corrections must update both bounds and agree with the app midpoint; fallback sources cannot supply a conflicting range.

`quarantine.json` documents ingredients whose source files lack a defensible required brewing value. Their fingerprints are explicitly excluded in `identities.json`, with their original keys reserved for later repair. They are counted in the build report rather than imported with a misleading zero. Once a supported value is found, remove the exclusion, add the reviewed correction and rebuild. This is distinct from the approved legacy exclusions.

`manufacturer-review.json` records the scope and gaps of a dated manufacturer check. Coverage of source files is not proof of coverage of a manufacturer's current range. Keep original liquid/dry forms, organic variants and distinct products separate even when they share text or a product code. The review does not certify every specification in every source pack.

## Verification

```sh
python3 -m unittest discover -s scripts/__tests__ -v
```

The source-derived descriptions and brewing data are generated locally. This pipeline does not grant redistribution rights or change the existing catalogue release gate. Preserve upstream notices and review source permissions before distributing generated data.

## Refreshing a disposable local recipe library

Stop the local application, then use the reviewed build to replace its ingredients:

```sh
python3 scripts/refresh-local-ingredients.py \
  --database /absolute/path/to/brewey.sqlite \
  --catalog .runtime/ingredients/catalog.json \
  --backup .runtime/backups/before-ingredient-refresh.sqlite \
  --discard-recipes
```

This operator command deletes all recipes and replaces all four ingredient tables, including custom ingredients. It preserves accounts, settings, beer styles and provider files. Recipe-dependent chat references follow the application's existing deletion rules. It requires an existing application database and a complete, valid catalogue. It creates a private SQLite backup, refuses to overwrite backups, and performs the refresh in one transaction with integrity checks and rollback on failure. It does not migrate old recipe references or change the bundled seed for future installations.


## Application setup

New application databases contain beer styles and no preloaded ingredients. After creating the first administrator, `/setup/ingredients` offers catalogue download with progress. The administrator can continue with a partial result or retry later in Settings → Ingredients. Existing databases and restored backups are not automatically reseeded.

Downloads run on the server using Python 3 (included in the Docker image). The shipped manifest is the only default download configuration; requests cannot supply commands, file paths or source URLs. `GET` and `POST /api/admin/ingredients` require an administrator session, and POST also checks request origin. Only one job runs per database. Interrupted jobs become retryable after their heartbeat expires; cached downloads are checksum-verified before reuse. Network work has a five-minute budget per attempt and the worker has a seven-minute overall limit.

Outputs and cache live beside the application database under `ingredients/`. A successful import is atomic. Retrying adds newly available records, updates unused catalogue records, and retains missing-source entries and all records already referenced by recipes. A failed build/import preserves the existing catalogue. Restore is blocked while a build is active. The job status and missing-source list survive application restart.

Operators can set `BREWEY_INGREDIENT_MANIFEST` to an absolute path to a curated manifest, `BREWEY_INGREDIENT_CACHE` to a private cache directory, or `BREWEY_INGREDIENT_OFFLINE=true` to use only local/verified cached files. These are server settings, not browser input. Custom manifests need their associated registry and local files. Generated downloaded catalogue data is not added to the image.

## Public release boundary

`legacy-identities.json` contains only old IDs and identity selectors for migration audits, not the retired catalogue or its descriptions. `frontend/src/lib/server/style-catalog.json` contains only style metadata. The small local supplement contains reviewed facts and original notes. All other descriptions are obtained during installation and remain subject to their source terms; see [NOTICE](../NOTICE.md). Do not commit download caches, generated output or private audit reports.
