# Agent harness

`types.ts` defines the provider-independent `AgentHarness` contract. `registry.ts` registers explicitly installed adapters and validates their declared connection, model, streaming, brewing tool, cancellation, reasoning and verbosity capabilities. Production currently registers only Codex; an unknown adapter fails explicitly without switching providers. `user-harness.ts` reads authenticated account selection and keeps adapter/user connections separate. `/api/agent` manages selection and adapter-scoped preferences; its account, models, login and cancel routes expose the unified lifecycle. Settings display only advertised controls. Existing Codex metadata is read during migration; new preferences live in `agentPreferences[adapterId]`.

The Codex implementation is a server-only adapter behind `AgentHarness`. `installation-context.ts` supplies current installation facts to the integrated agent without secrets or infrastructure paths. Chat supplies its current prompt, quoted history, tool schemas, event sink, and authenticated request-scoped tool executor. The adapter maps Codex text, reasoning summaries, brewing calls/results, completion and errors to Brewey's existing SSE payloads. It owns tool SSE events, so the callback must not emit duplicates.

Each local Brewey user gets a selected adapter and a private persistent `CODEX_HOME` (for example `.runtime/codex/<userUUID>`). This must never point at a desktop/CLI home or contain copied personal credentials. The child receives an isolated `HOME`, file-based credential storage, a small environment allowlist and disabled shell/code-mode/apps/hooks/web-search/subagent features. Use an empty application-owned working directory. Run the service as its own non-root container user; the adapter's configuration is not a replacement for an OS/container security boundary. Protect this volume and keep it out of Git/backups exported to other users.

Brewey's UI and login route offer ChatGPT device-code login only. Display the returned verification URL and code; poll `account()` for completion or subscribe with `onNotification`. Device authorization must be enabled for the user's account/workspace. The low-level adapter retains browser login support for a possible future native client, but it is not exposed by Brewey: the Docker deployments do not configure localhost callback access. No API-key login, paid provider, account migration or ambient API token fallback is implemented.

`models()` returns the actual app-server catalog, including supported reasoning efforts. Omitted chat model selects its declared default. Catalog membership does not prove plan entitlement: only a successful turn verifies the selected model for that request. No model is silently substituted. Failed/interrupted turns do not produce a successful `done` event.

`reasoningEffort` is checked against the selected model's advertised efforts and sent as `turn/start.effort`. `showReasoning` independently controls summaries and their display. `verbosity` accepts `low`, `medium`, or `high` and is sent as `thread/start.config.model_verbosity`; it is not a turn field. Omitted effort preserves the selected model's reported default. Omitted verbosity uses Brewey's explicit Low default, shared with the UI and checked against the pinned adapter contract. The pinned binary's internal bundled catalogue declares native verbosity support for its models, but the public `model/list` response exposes neither a verbosity capability nor its default. Do not invent public capability metadata or assume this remains true after a binary/catalogue change.

Conversations can opt into native durable threads with `persistent: true`. A new thread uses `ephemeral: false`; `onThreadReady` is awaited before `turn/start` so the application saves the ID under the authenticated conversation. Subsequent turns use `threadId` and native `thread/resume`, update developer instructions and include the latest application context in that turn. Saved transcript history seeds only a new/rebuilt thread and is never duplicated on resume. Legacy callers without persistence retain ephemeral behavior. Native rollouts now contain private conversation/recipe/tool data in the per-user home; protect that volume alongside its authentication state. Only registered dynamic tools in namespace `brewing` may reach the executor, which must enforce authenticated recipe ownership and validate arguments. Abort reaches both `turn/interrupt` and the callback's signal. A callback that ignores cancellation can still finish a mutation after cancellation or timeout; check the operation's actual outcome before retrying it.

Protocol is pinned to the Codex CLI `0.159.2` schema generated using `codex app-server generate-ts --experimental`. Dynamic tool schemas and their bidirectional `item/tool/call` flow are experimental. Review generated schemas and run tests before upgrading the binary. Official references: [App Server](https://learn.chatgpt.com/docs/app-server), [Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference). Keep the adapter behind authenticated application routes and verify compatibility before upgrading it.

Run the no-network protocol tests with Node 24:

```sh
node --test --test-isolation=none frontend/src/lib/harness/__tests__/*.node.mjs
```

The fake peer verifies credential/environment isolation, model selection, streaming, tool allowlisting, failure handling, cancellation, concurrency, timeouts and reconnection. Live sign-in and inference require a disposable application-owned account and are separate release acceptance checks. Optional smoke scripts use fresh unauthenticated homes and never send an inference turn.

The independent synthetic adapter regression exercises the same account/model/login/tool stream/error/cancel contract without Codex wire fields. It is test-only and does not register a second production runtime. To add a real adapter, implement the generic contract and register its descriptor, capabilities, storage namespace and factory explicitly; use its application-owned home, validate live model settings, and never copy CLI credentials or supply a paid fallback.


`AgentCapabilities.persistentThreads`, `contextCompaction` and `automaticCompaction` describe optional native lifecycle support. `compactThread({threadId, abortSignal, onEvent})` resumes the native thread and starts `thread/compact/start`; the RPC acknowledgment is not completion. The adapter waits for the matching thread/turn, the same `contextCompaction` item's start/completion, and a successful `turn/completed`, then emits only `{type:'context_compacted',thread_id,automatic:false}`. Automatic compaction emits the same status with `automatic:true` after a successful turn. No internal compaction summary or hidden reasoning is exported. Chat, compaction, deletion and account changes share one busy guard; cancellation reaches native `turn/interrupt`. Native compaction can consume the connected account's inference allowance; unauthenticated live smoke tests deliberately do not invoke it.

Pinned 0.159.2 restores the original dynamic tool schemas on resume and has no `dynamicTools` resume parameter. A private schema fingerprint under `CODEX_HOME/brewey-thread-tools` detects tool/schema/unit changes across process restarts. `THREAD_TOOLS_CHANGED` or a native missing rollout (`THREAD_MISSING`) is a pre-inference error: the authenticated application may explicitly rebuild on the same adapter from its saved transcript. Other resume errors are `THREAD_RESUME_FAILED` and do not permit automatic replay. Errors after `turn/start` are never classified as rebuild-safe. A persistent thread with zero turns has no native durable rollout yet; a crash between binding and first turn therefore also requires this missing-thread recovery.

`deleteThread(id)` uses native `thread/delete`, which permanently removes persisted rollouts/metadata, rather than archiving. The application must verify conversation ownership before invoking it; the adapter checks native ID syntax and resolves only within its isolated home. Schema markers are removed after successful native deletion. Official lifecycle reference: [Codex App Server](https://learn.chatgpt.com/docs/app-server).

The opt-in `node frontend/src/lib/harness/__tests__/codex-lifecycle.smoke.mjs` verifies persistent-start schema acceptance, genuine native deletion and the exact zero-turn/missing-rollout behavior against a fresh unauthenticated 0.159.2 home. It sends no `turn/start` or compaction request. Synthetic tests cover persisted resume across peer-process restart and compaction lifecycle; authenticated native resume/compaction remains a deployment acceptance check.
