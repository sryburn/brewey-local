# Saved brewing conversations

SQLite is the authoritative chat history for each signed-in Brewey account. Refreshing, reopening the app or signing in on another device restores the current conversation. Browser storage and desktop Codex history are not imported.

There is one current conversation per account, with any number of saved conversations. Selecting a recipe changes the recipe pane and the context supplied on the next message; it never switches chats. Explicitly resuming a chat restores the recipe selected when its last ordinary user message was sent, if that recipe still exists and belongs to the signed-in account. A missing/deleted selection leaves the current recipe unchanged; it never falls back to an older turn or a recipe merely read/modified by the agent. `/compact` does not replace the last message's selection. Ordinary refreshes never restore selection, and a newer manual choice made while resume is pending takes precedence. Recipe context and brewer profile are refreshed from the authenticated brewing core before every turn, and the agent is explicitly told when no recipe is selected. Historical associations are not treated as the current recipe.

Recipe associations are searchable history metadata. Each accepted user turn records its selected recipe. Successful agent tools record recipes read or modified, using the authenticated core's actual result (including the actual parent of a modified ingredient). Recipe searches associate the returned recipes as read; cloning associates the source as read and the clone as modified. Failed operations do not claim successful activity. Selection changes without sending a message do not tag the chat. Sessions can involve multiple recipes, and `/resume` and `/status` display their names and activity labels. Current names and historical name snapshots remain searchable after rename; deleted recipes keep historical tags and do not make the conversation read-only.

Type `/` in the composer to discover commands, then narrow the suggestions by typing. Arrow keys select, Tab completes, Enter runs, and Escape dismisses. Suggestions can also be tapped. `/help` has been removed; `/` is the command list. `/resume` focuses its search field, `/rename` selects the title, other panels focus Close, and closing or changing chats returns focus to the composer when it was in use. Initial mobile page loads do not summon the keyboard. Desktop provides shortcuts below the input; mobile uses the same slash commands without a separate management toolbar. Command feedback stays outside the durable brewing transcript.

- `/new` starts a fresh conversation and preserves the previous one. `/clear` remains an alias.
- `/resume` opens chats with saved messages. Empty chats are omitted from both history and search, even if renamed; they become visible after their first saved message. Use ↑/↓ to highlight an available chat and Enter to resume it; focus stays in the search field for typing. Escape closes the panel. Search matches literal case-insensitive substrings in chat titles, current and historical associated recipe names/IDs, chat IDs and the complete saved message text, including messages not loaded in the pane. Results remain ordered by recent activity. Search is performed locally by the authenticated server; no agent request is made.
- `/compact` reduces agent working context while retaining the readable transcript. `/status` shows the chat title, recipe activity and context status.
- `/delete` opens confirmation for permanent removal of the selected chat and tracked native threads. Recipe changes are preserved. Changing the selected chat invalidates the confirmation.
- Scroll upward near the top to load earlier saved messages automatically while retaining your reading position. `/reload` retries loading after a connection error; `/stop` stops a response on this device.
- New chats initially show **New chat**, then receive a short title from the first accepted user message, derived locally with Unicode-safe truncation. `/compact` does not name chats. Existing historical titles and explicit names remain unchanged. `/rename` opens a focused title editor; `/rename My brewing discussion` saves directly. Names are whitespace-normalized, limited to 200 UTF-8 bytes and session-owned; renaming preserves transcript, recipe metadata and agent context.
- `/settings` opens agent/model/thinking/verbosity preferences; `/profile` opens brewer settings. Existing `/import`, `/export`, `/print` and `/debug` remain available; `/cancel-import` removes the pending file and exits import mode.

There is no General/recipe mode, scope filter or composer mode label. `/mode`, `/general`, `/recipe`, `/help` and `/older` are absent. Commands that change a conversation are blocked while it is busy. Recipe memory summaries, background memory inference and external memory services are deferred; this release only records useful history metadata.

## Working context and compaction

The installed Codex adapter starts persistent native threads in the account’s private application `CODEX_HOME`. Later turns resume the same native thread. IDs and exact tool-schema fingerprints remain server-side; clients cannot choose native threads or supply replacement history. Changing agent adapters preserves the conversation and supplies its saved history to the selected adapter. Adapters never silently substitute for each other.

Codex can compact automatically. `/compact` and its desktop shortcut request native compaction and wait for confirmed completion. They preserve the readable SQLite transcript, including tool results. When native continuation is unavailable, a no-tools summary through the same selected adapter plus the recent transcript forms portable working context. Long portable histories are summarized automatically in bounded chunks; they are not silently truncated. Failed or cancelled compaction keeps prior history/context intact.

A missing native rollout or changed brewing tool schema can rebuild context from saved history before inference starts. Other failures cannot automatically retry a started turn. Historical tool calls are read-only context, never replayed actions. External activity notes also invalidate stale native bindings.

## Interruption and synchronization

One running turn per account prevents competing tools and native-thread updates. SQLite records accepted messages, partial text, reasoning summaries and tool outcomes before they are rendered. Stop or a lost connection retains accepted work; completed recipe changes are not rolled back or retried automatically. Request IDs prevent duplicate turns. A two-minute renewable lease recovers abandoned turns after a process failure, retaining their partial transcript. Tool execution revalidates the lease and browser session.

Idle clients refresh history/status every five seconds and on focus. They cannot send while another device has a running turn. Earlier messages load in batches as you scroll up; compaction does not delete them. The number of messages loaded by the browser does not limit the harness’s working context.

These browser conversation routes require the local session and same-origin mutations. PATs remain for the public brewing API, not account or agent history/settings. Brewing tools continue through `BrewingApplication` and its verified principal. Native thread storage is private application data and part of the persistent named volume; no desktop credentials, filesystem access or developer-funded inference are introduced.

## Backup and rollback

Schema 4 adds per-turn recipe activity and converts the old recipe/General scopes into a single current conversation per account. The most recently updated previously active conversation remains current (ID breaks ties); other previously active conversations become saved history. Old recipe attachments become historical tags, including deleted-recipe references. Existing titles, messages, turns, events, summaries and native thread bindings remain intact. Recipe deletion no longer archives the chat. Historical tags are kept at conversation level rather than inventing recipe activity for old individual turns.

Native online backups include conversation and activity tables; explicit JSON exports/imports preserve owned transcript, summaries, recipe metadata and thread references. Restored running turns become interrupted, preventing automatic action replay. A database-only restore can rebuild missing native context from the saved transcript.

Before upgrading a deployment, preserve its image, configuration and a consistent database backup. Older images cannot open a newer database schema: rollback must restore the matching pre-upgrade database with web stopped, removing stale WAL/SHM companions. Do not discard subsequent owner activity when planning recovery. See [deployment.md](deployment.md) for the protected-volume procedure. SQLite backups and native thread files contain private chat data; keep them protected alongside account credentials.
